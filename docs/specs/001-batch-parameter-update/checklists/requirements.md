- **Validation iteration 5 (Model Group edge case, research-backed)**: The stakeholder requested research into how Revit 2025-2027 handles elements that belong to a Model Group when the batch tool tries to write an Instance or Type parameter, and asked for the resulting edge case to be incorporated. Web research (The Building Coder, Autodesk's Developer Blog, and Autodesk/Dynamo/McNeel forum threads, current as of Revit 2026) confirmed a long-standing Revit API limitation: there is no programmatic "Edit Group" scope, so writing a parameter on a grouped element from outside interactive Edit Group mode either throws a hard failure (group type has more than one instance) or only "succeeds" via an unstable, community-discouraged warning-suppression workaround (single-instance groups) that can corrupt or crash large models; the only Autodesk-documented alternative is an "ungroup, edit, regroup" pattern also flagged as cumbersome/unstable. No source was found suggesting Type-level updates (which target the shared Type/Symbol object, not the grouped instance) are subject to the same restriction, so that expectation is recorded as an assumption to re-verify during implementation rather than a confirmed fact. `spec.md` was updated accordingly and re-validated; all 16 items remain green, and no `[NEEDS CLARIFICATION]` markers were introduced.
  - *What changed*: A new Instance-path edge case (proactive skip, 400) was added stating the tool never attempts the write, never enters Edit Group mode, and never auto-ungroups/regroups; a new FR-025 requires this proactive membership check ahead of any write attempt, cascading a renumber of every subsequent FR from the old FR-025–FR-047 to the new FR-026–FR-048 (all cross-references, including the one numeric citation in the NDJSON-metrics FR, were checked and updated); FR-033 (per-element 400 classification) and the "Batch Execution Result" Key Entity were extended to list Model Group membership alongside workshared-ownership conflicts; a new Acceptance Scenario (User Story 4, scenario 4) and Independent Test wording cover both the Instance-path skip and the Type-path's expected unaffected behavior; a new Assumptions bullet documents the research finding, its sourcing, and the caveat that the Type-path expectation needs re-verification; a new Out of Scope bullet excludes automatic ungroup/regroup or programmatic Edit Group entry; and a new Success Criterion (SC-013) makes the proactive-skip behavior independently measurable.
  - *Re-check against this checklist*: Content Quality still holds — the addition is a business/UX rule (skip grouped elements proactively, don't restructure the model) grounded in a platform constraint, not an implementation detail; the constraint itself is disclosed in Assumptions the same way the multi-version build pattern and Velopack were already cited. Requirement Completeness still holds — FR-025 and the FR-033 extension use the same testable "the system MUST ..." phrasing as every other FR, the caveat about the unverified Type-path expectation is stated explicitly rather than left as a silent assumption, and no ambiguity required a `[NEEDS CLARIFICATION]` marker. Feature Readiness still holds — User Story 4's scenarios, the Key Entities, and Success Criteria SC-001–SC-013 remain mutually consistent after the renumbering, which was spot-checked line-by-line against the full FR list to confirm no gaps or duplicate numbers remain.
